# GazeConnect Pro - Project Context

## What This Is
AAC (Augmentative & Alternative Communication) app for ALS/MND patients using Tobii Eye Tracker 5. Built for Papa — and for every ALS patient who deserves to communicate freely.

## Architecture
- **Frontend**: Electron 44 + React 18 + TypeScript + Vite 5 (Node.js 22.12+ for development, Electron 44's floor)
- **Backend**: Python 3.10+ (asyncio WebSocket server on port 8765)
- **Eye Tracking**: .NET 8 x64 self-contained TobiiGazeHelper (TCP port 5555)
- **TTS**: offline Kokoro-82M v1.0 ONNX CPU, af_heart only (spawned Python worker; no system/browser voice fallback)

## Key Constraints
- ALL UI must work with eye-gaze (dwell-based selection, NO drag/drop)
- Minimum primary gaze target: 80 CSS pixels; physical size depends on display density and scaling.
- Must support 13" to 27" screens (use clamp() and viewport units, NOT fixed px)
- Dark mode is primary (reduces eye strain for ALS patients)

- Selection durations live in `src/config/dwellTimeConfig.ts` as exactly **ten** complete timing sets of the same **eight** action groups. History of 8 Oct 2026: first (maintainer: every set felt slow, even Balanced) Quick, Brisk and Balanced got keys of 0.6, 0.75 and 1.0 s; second (those were too fast for Papa, who managed only Relaxed, then keys 1.7 s, and with practice) Calm took that Relaxed and slower sets followed, and word suggestions became a little longer than keys; third, a mode between each of the slower ones and a clearly longer YouTube bar. Fastest first, in ms for Typing / Alphabet groups / Communication / Navigation & choices / Deliberate actions / Urgent Needs / Video controls / Word suggestions: **Quick** 600/550/650/700/800/1450/1000/650, **Brisk** 750/700/800/850/1000/1500/1200/850, **Balanced** 1000/950/1050/1150/1300/2000/1600/1100, **Moderate** 1300/1200/1350/1500/1700/2600/2100/1450, **Calm** 1700/1600/1800/1950/2200/3400/2700/1850 (default for new profiles), **Restful** 1850/1700/1950/2150/2400/3700/2950/2050, **Relaxed** 2000/1850/2100/2300/2600/4000/3200/2200, **Leisurely** 2200/2050/2300/2550/2850/4000/3500/2400, **Unhurried** 2400/2250/2500/2750/3100/4000/3850/2650, **Extra Time** 2800/2600/2950/3200/3650/4000/3900/3100. Keys fill in 0.6, 0.75, 1.0, 1.3, 1.7, 1.85, 2.0, 2.2, 2.4 and 2.8 s: about 1.3x a step up to Calm, then about 1.1x (near one just-noticeable difference), so a person can settle on a pace exactly; Unhurried and Extra Time have the key times Relaxed and Extra Time had on 5 Oct. A profile saved on Measured (5 Oct: keys 1.7 s, retired) selects Calm, which has them (`normalizeDwellTimingSet`, also applied when settings load). The values against published practice: fixed eye-typing dwell is usually 450-1000 ms (Mott et al., CHI 2017; Spakov & Miniotas 2004); GazeTalk suggests 1000 ms to start; practised users reach 300-500 ms (Majaranta et al., CHI 2009); OptiKey's default is 250 ms lock-on plus 1250 ms. One rule for every set: a group is the key time times `GROUP_RATIOS` (1 / 0.93 / 1.05 / 1.15 / 1.3 / 2 / 1.6 / 1.1), to the nearest 50 ms, within `GROUP_LIMITS` (Urgent Needs 1.45-4 s, the video bar 1-3.9 s so Urgent Needs stays the longest), and no selection takes longer than 4 s (`MAX_DWELL_MS`). Keys stay the quickest: word suggestions and the phrase cell take a little longer (1.1x: choosing one puts a whole word in the message), cards, pages, the nav bar and SHOW NAV 1.15x. Keys, Shift and the words on the Quick Words board (`quickWordChoice`; urgent words stay `medicalUrgent`) share the key time, for muscle memory. On the keyboard: letters, Shift, BACK, SPACE and 123 take the key time, suggestions 1.1x, Speak 1.05x, Quick Words / SHOW NAV / FULL SCREEN / the nav bar 1.15x, Delete Word and the gaze toggle 1.3x. **Urgent Needs** (`emergencyButton`) stays deliberately the longest selection in every set: twice the key time, from 1.45 s up to 4 s (1450 Quick, 2000 Balanced, 4000 from Relaxed); it answers even with gaze off, so a resting look must not set it off. **Video controls** (`videoControl`): every control of the YouTube player bar, which Focus/Serene draw under the video right below the subtitles, takes 1.6x the key time, from 1 s up to 3.9 s: clearly more than everything but Urgent Needs (third request), so a passing look while watching chooses nothing. Their progress banking is deliberately unchanged: the bar sits on the bottom screen edge where the raw stream flashes away and back (see the gaze-bubble bullets), and banking is what makes a long dwell there achievable. Settings shows each set with its ring times ("Keys 1 s · cards 1.15 s", `describeTimingSet`); the practice tile still previews onset before ring fill. The person chooses one set in Settings -> Selection Speed; the ten sets replace any manual timing. Do not add per-button sliders, multipliers or repeat-key acceleration, and keep the sets proportional. The embedded browser accepts only `ALL_DWELL_DURATIONS_MS` and defaults to the Balanced navigation time (1150 ms); `npm run check:dwell-groups` fails if its two literal lists (or the browser replay's) drift from the config, a set loses the ratios, Quick / Brisk / Balanced / Calm change their keys and cards, Urgent Needs stops being the longest, or the YouTube bar / Quick Words board change group, and `npm run check:gaze-safety` measures a key against a word suggestion in every set. Onset/cooldown and tracking safeguards are separate internal controls. After a key, a different key may begin after `keyboardNextKeyWaitMs`: 0.4 of the key time, from 250 ms up to the stage's keyboard cooldown (Quick 250, Brisk 300, Balanced 400, Calm 500, Relaxed 700 ms at the default stage; until 8 Oct 2026 a fixed 700 ms, longer than a key at Quick); the same key still waits the stage cooldown, so a look that stays on it repeats no sooner. Letter to letter at Balanced, the eyes moving at once: 0.4 + 0.15 + 1.0 = 1.55 s (1.85 s with the fixed wait, 2.25 s on the old table). Elsewhere the next selection can start 1.42 s after one, and a new screen takes no gaze for its first 1.2 s (Smart pause).

The window is shown maximised, then full screen is requested once it is visible and opaque, after a 400 ms settle (`enterStartupFullScreen` in `electron/main.ts`); `GAZECONNECT_START_FULLSCREEN=0` starts maximised as before. - Electron's main process must survive losing the console that launched it (terminal closed, launcher gone). Its stdout/stderr then become broken pipes; a failed console write used to become an uncaught exception whose handler logged again and failed again, forever: the main thread spun at 100 %, stopped answering IPC and window messages, and could not remove a web page it was asked to close (stack read from the hung process on the rig, 22 Sep 2026). `electron/stdioGuard.ts` is installed first thing in `main.ts`; it owns the `uncaughtException` handler and moves later log lines to `tools\reports\main-console-*.log` (installed app: Electron's logs folder). Never add a handler or logger that writes to the console without it.
- The embedded web page (YouTube, Quick Search) is a native `BrowserView` drawn over the whole window, not part of the DOM: nothing in React removes it. Closing it detaches it from the window first, then gives the page's own cleanup at most 400 ms (`electron/browser/browserViewController.ts`); never await a page script before the view is off the window (`executeJavaScript` waits indefinitely while a page is loading, which left YouTube over the Home screen). Every open/close/reset takes a ticket so a stale open can neither resurrect a page nor close its successor, the interface closes any page whenever it is not on the web screen or reloads, and the main process closes it when the interface reloads or its renderer dies. `BrowserView` is deprecated since Electron 30 but still ships in 44 and works (26 Sep 2026, driven through `window.electronAPI.webview`: open, navigate, back/forward via `webContents.navigationHistory`, close with nothing left behind; the interface no longer runs scripts in pages, see the 6 Oct 2026 entry below); replacing it with `WebContentsView` is a separate change that needs the rig.
- Embedded page load (28 Sep 2026; YouTube browsing seemed to hang after two or three videos). Each gaze request runs the in-page dwell loop on the page's own main thread, and YouTube's watch page grows with every video it plays in place (6,000 to 16,000 elements and a 72 to 224 MB heap over six videos). Our requests had kept YouTube's main thread 40-60 % busy while a video merely played (6 % without gaze). They came at the Eye Tracker 5's ~66 a second, moved the ring by `left`/`top` (a page layout per move) and searched the whole document for a skip-ad button every 300 ms (~22 ms each). Around each video switch they then queued behind YouTube's own work past the 150 ms freshness limit, and the page discarded them by design, hiding the ring and restarting the dwell: the eyes seemed to stop working. Now page requests start at least 25 ms apart (`BROWSER_GAZE_MIN_INTERVAL_MS` in `electron/main.ts`: ~33 a second, the rate the page loop was built for; dwell is timed by the clock, not by frames). The ring moves by the compositor `translate` property on its own layer (`drawCursorAt`). The skip-ad search covers the player every 300 ms and the whole document at most every 2 s. The cursor stylesheet is kept to one copy per page instead of one more per video. Measured on the rig with 66 Hz gaze on a playing video: YouTube's main thread 54 % -> 24 % busy, page requests answered in 5 ms at the 95th percentile instead of 16. Do not move the ring by `left`/`top` again or send the page every tracker frame: `npm run check:browser-cursor` and `npm run check:browser-gaze-safety` fail if either returns. Separately, this Intel Iris Xe (driver 31.0.101.5333) stops presenting frames for up to about 2.5 s while a new video's hardware overlay is set up (a Chromium trace shows the display compositor waiting for a presentation acknowledgement while the GPU process is idle). That stall is in the graphics driver, not the app, and it clears by itself.
- **Whole-app freeze while watching YouTube (investigated 9-10 Oct 2026).** On the maintainer's 8 GB laptop (7.7 GB usable, Iris Xe) nothing in the app responded for a long time after two or three videos (Next, More Videos), then it recovered by itself; Windows logged no driver reset or app hang. Measured in a 14-minute, 17-video soak of the real app: GazeConnect used 640-1080 MB private (page 230-535, GPU 210-400, interface about 90, main about 60) with no growth across videos, but the computer had 160-760 MB available with 13.5-15.9 GB committed, read back up to 8,000 pages a second from disk (above 1,000 a second in a third of the samples) and kept the disk up to 95 % busy: Windows was paging the app's own processes out, and one GPU process draws both the interface and the page. Also found: a Kokoro voice worker left by an abruptly closed app held about 400 MB for two days (`python/services/process_lifetime.py` now ends every spawned worker with the backend: the venv launcher's job object ends only the backend, and the workers silently break away from it; `python -m unittest tests.test_tts_available` kills a stand-in backend and checks); a Next after which YouTube reloaded the whole page and played the same video again (the bar now presses Next once more if the same video is still there 7 s later with no page change between, `NEXT_CHECK_MS`); and work piling up in a busy page (the page-work limits, probe and rebuild above). The health log (`electron/healthRecorder.ts`) writes a line every 5 s to `<profile>/logs/health/health.jsonl` (memory and CPU per process, the computer's available and committed memory, main-process delay, the interface's heartbeat and worst frame gap, the page's oldest waiting script; pages by kind, never address) and events as they happen (page slow / answering / rebuilt, a process gone, a gap in the samples = the main process stood still); after a freeze, its last lines say which part stopped first. Fault injection in the real app (`scratchpad` probe, 10 Oct): a page held busy 12 s brought the bar with Back in 6.3-7.4 s and answered again after; held busy 45 s, it was rebuilt after 24 s in a new process, the video resuming at its time and full screen coming back. Ending the old process and loading the new page at once left the new page waiting for its first response for good (1 of 2 trials), so the rebuild waits for the old process to go (`processGone`, at most 5 s). IPv4 addresses carried in IPv6 (`[::ffff:7f00:1]`, the hex form the URL parser writes) are now refused like their IPv4 form (`embeddedIpv4`).
- **Embedded browser: safety, resources and gaze controls (6 Oct 2026, maintainer request: YouTube and web browsing must not hang, use little memory, have few selection points, scroll properly and be safe on any Windows laptop).**
  - *Safety* (`electron/browser/browserSafety.ts`, `electron/browser/pagePreload.ts`). Pages use their own persistent session `persist:gazeconnect-web`. It refuses:
    - every permission except sanitized clipboard writes, so no camera, microphone, location, notifications or `openExternal` launching of other Windows programs;
    - device choosers, downloads, and any request to this computer or the local network (the backend on 8765 and the floor-plan server on 5050 are unreachable from pages).

    Spell checking is off. Pages and redirects are public http(s) only (`isAllowedPageUrl`), pop-ups are denied, "Leave site?" cannot hold the patient, `<webview>` is refused everywhere, and the interface window can neither navigate nor open windows. The sandboxed page preload stops alert/confirm/prompt, printing, file pickers and passkey prompts, and exposes nothing to pages. A refused download, link or pop-up shows one line on the page's status line, at most once a minute per kind.
  - *Retired channels.* The interface can no longer send scripts, keystrokes or clicks into a page: `webview:executeJs`, `webview:type` and `webview:click` are gone. YouTube full screen is the named command `maximize` / `restore` / `is_maximized` (`youtubeController.ts`). `npm run check:browser-safety` fails if a retired channel returns. Do not add a channel that runs arbitrary script in a page.
  - *Resources.*
    - History is capped at 30 entries.
    - Memory (rewritten 10 Oct 2026, see the freeze bullet below): every 15 s `browserMemoryAction` weighs the page's own memory against a budget scaled to the computer (`browserMemoryBudgetMb`: soft 9 % of RAM, 450-1400 MB; hard 15 %, 750-2400 MB) and the computer's available memory against `systemMemoryLimitsMb` (low 7 %, 400-800 MB; critical 3.5 %, 250-400 MB). Past the soft budget, or on a computer short of memory with a page of 450 MB or more, the page is built again at the next change of video (a real one: another page or video, `samePageAndVideo`, since YouTube rewrites the address of the video being watched and a rebuild there restarted the page during More Videos); past the hard budget, or on a computer critically short with a page of at least 450 MB (or 80 % of its budget), at once. A rebuild (`rebuildBrowserPage`) ends the old page's renderer process and makes a new page in a new process, the video resuming where it was, for memory at most 4 in 10 minutes and once a minute, for a stuck page at most 3 in 10 minutes (separate budgets, so memory rebuilds can never use up a stuck page's). The interface is told first (`webview:notice` refreshed / recovered) and keeps its page and full screen; it is never told the page closed. YouTube pages measured 230-550 MB, a freshly built one included, so a page about that size is never interrupted for memory. The floors before were 750 / 1100 MB, above anything a page uses, so a 4 GB laptop never refreshed at all, and the refresh reloaded inside the same process.
    - A page that stops responding: Chromium's `unresponsive` (unanswered input events) still restarts it after 8 s more, at most 3 times in 10 minutes, then closes it. Gaze requests are scripts, not input events, so the page watch (`checkPageResponding`, every second) also sends a tiny probe after any script left unanswered 3 s: answered, the older scripts only lost their answers; unanswered 3 s more (about 6 s in all), the interface shows the bar with Back even in calm full screen (`webview:notice` slow, repeated every 15 s while it lasts); unanswered 20 s (about 23 s in all), the page is rebuilt. A load still waiting for its first response after 20 s is asked for once more.
    - Every page script gives up after 5 s (`withPageTimeout`), but a script given up on still runs in the page later: `executeJavaScript` cannot be cancelled. So the scripts waiting in the page are limited per kind (`pageWork.ts`): two gaze scripts (the gaze gate gives up a request after 1.5 s, `BROWSER_GAZE_REQUEST_DEADLINE_MS`), one playback poll, one of each YouTube command (four in all; another is answered `page_busy` at once), one Up / Down. Before, a busy page collected one more script every few seconds from each poll (10 at once measured) and ran them all together when it recovered, and one lost answer stopped gaze selection on the page for good. The HTTP cache is capped at 384 MB at start.
    - The YouTube bar reads the page one request at a time every 1.2 s, and not at all while the search keyboard is shown; an answer `page_busy`, or one asked of a page since replaced, changes nothing.
    - Quiet page: while the page cursor is off for 2 s (watching, gaze paused) the in-page change watcher (`MutationObserver`, which serves only gaze selection on the page) is disconnected (`gcSetQuiet`, asked by the playback poll), and the next gaze request reconnects it with a hard epoch.
  - *Up / Down* (`webview:scrollPage`, `electron/browser/pageScroll.ts`). The page itself scrolls the document, or the panel that really scrolls, by 80 % of the view with smooth scrolling, and reports top and end; the buttons dim there but still answer. This replaced the mouse wheel at the view centre, which on YouTube landed on the video and did nothing (the patient's "scroll button is not working").
    - *YouTube's own reset (fixed 8 Oct 2026).* About 0.6 s after a new page's data arrives (`yt-page-data-updated`), YouTube's code puts the page back to its top once more (`html.scrollTop = 0`), which undid an Up / Down pressed in that time: every fast Down after a Back in the end-to-end run (4 of 4). The page cursor script now records YouTube's navigation times (`window.__gcPageNav`: `yt-navigate-start`, `yt-page-data-updated`); Up / Down waits while YouTube is still loading the page and until 1 s after its data (`YOUTUBE_RESET_SETTLE_MS`; at most 3 s in all), then scrolls, and for 1.5 s afterwards puts the page back where it was sent if it is put straight back to its top (a jump of 40 px or more; a gradual move such as Gaze Scroll is left alone). Top never waits, and Back to Video's Top ends a waiting press (main lets Top through while a press is in flight). Other sites never wait. `npm run check:page-scroll` (13 checks on a virtual clock); live, the same fast sequence now scrolls in 4 of 4 (the press is answered 1.4-1.9 s later, once YouTube has finished).
  - *The dock beside every page* (`ContentScrollDock` in `WebBrowsingScreen.tsx`): Up, **Gaze Scroll**, Down, plus **Full Screen** on a YouTube video page in Browse. Gaze Scroll (On/Off) is the main-process edge scrolling (`webview:setScrollMode`): resting the eyes in the top or bottom fifth of the page for 650 ms moves it gently, never during a page dwell. It works in Look Only and Read too (the page then gets cursor-less gaze frames, so nothing on it can be selected), is turned off when a video takes the Watch bar, and the status line says when it is on and which way it is moving. The maintainer asked on 6 Oct 2026 for no navigation, scrolling or full-screen option to be lost, so it came back next to Up/Down.

    - Watch (a video page): the page takes no gaze. Its bar has Back, Pause/Play, Next (Skip Ad in its place while an ad can be skipped), Full Screen, More Videos and Search.

    - Skip Ad presses that button with a real click at its centre (8 Oct 2026, maintainer report: Skip Ad not working). `skip_ad` answers a `trustedClick` and the main process sends it with the page-zoom correction, as for a dwell click. Checks: `check:youtube-page`, and the live run presses Skip Ad once per ad and needs the ad gone within 2.5 s.

## Development Commands
- `.\setup.bat` — Prepare this checkout: `npm ci --ignore-scripts` (skipped while `node_modules` matches `package-lock.json`; no package's install script runs, none is needed on Windows) followed by Electron's own program, which Electron 42+ no longer fetches during install: `node_modules\electron\install.js` downloads it, checks it against the locked package's `checksums.json`, and does nothing when it is already there, so no launch ever downloads it or fails offline. Then `python\.venv` with the versions pinned in `python/constraints.txt` (applied on the 3.12 baseline), and the helper build (`--simulate` skips it). The interpreter comes from the `py` launcher (3.12 first), never from PATH order: an older Python 3.9 comes first on the maintainer's PATH and once left a 3.9 venv without packages. A broken or unsupported `python\.venv` is rebuilt; `--force` reinstalls both; `-Python <path>` or `GAZECONNECT_PYTHON` chooses the interpreter. It refuses to run while this checkout's app runs. Its stamps (`python\.venv\gazeconnect-setup.json`, `node_modules\.gazeconnect-setup.json`) are read by start-dev, check-windows, status-dev and build-installer, which stop with "Setup is needed" when the requirements, constraints or lock changed since. To update pins: install requirements without the constraints in a fresh venv, run the tests and a launch, then `pip freeze --all --exclude pip` into `python/constraints.txt`
- `npm run dev` — Start Vite dev server (UI only, for rapid iteration)
- `.\start-dev.bat` — Full app (Electron + Python + Tobii). The interface is the BUILT one from `dist`, rebuilt automatically when a source file is newer than the build: measured 23 Sep 2026, the window is on screen 7 s after the launch instead of 25-32 s
- `.\start-dev.bat --hot` — Same app, interface served by Vite with live reloading. Slower to start, and the only mode where an edit reaches an app that is already running (so never use it while the maintainer is testing)
- `.\start-dev.bat --simulate` — Without eye tracker (mouse-as-gaze mode)
- `.\start-dev.bat --quiet` — Same launch with output written only to `tools\reports\dev-*.log` (use this for agent-driven runs)
- `.\stop-dev.bat` — Close the running development app from any terminal (only processes from this checkout). `--force` additionally stops a program outside the checkout that holds 8765 or 5555, after naming it
- `.\status-dev.bat` — What is running from this checkout and who holds each port; changes nothing (exit 0 ready, 1 running, 2 a fixed port is held by something else)
- Launch port handling: a previous GazeConnect (this checkout or the installed app) is closed automatically; the interface server (5173-5183) and floor plan server (5050-5060) take the next free port; backend 8765 and helper 5555 stay fixed, and a foreign program holding them is named, never stopped.
- `.\build-installer.bat` — Build production .exe installer
- `.\check-windows.bat` — Finite Windows dependency, DLL and port readiness checks after setup

## Runtime Logging Safety
- Never run the live gaze app directly in Codex with continuous stdout logs.
- For runtime checks, redirect logs to a file and inspect only tail/grep output. The launcher streams to the maintainer's console by default; agents launch with `--quiet`.
- Disable high-frequency gaze logs by default. Use `GAZE_DEBUG=1` only when needed.
- `tools\reports\dev-*.log` is UTF-8 without a BOM in both launch modes (26 Sep 2026), so grep and tail read it directly; logs from before are UTF-16LE (`iconv -f UTF-16LE -t UTF-8`). With `--quiet`, cmd.exe writes the file, so it keeps filling even if the launcher is killed.
- On the maintainer's machine, every `powershell.exe` started from an agent session was ended from outside after 15-180 s (exit code 127 or -1; Python and Node processes beside it ran on; measured 26 Sep 2026), and a maintainer launch once stopped the same way. A setup, installer build, launcher or stop-dev that ends without a message was stopped like this, not broken: run it again. Setup resumes safely (nothing counts as verified until it finishes), the app keeps running when its launcher dies, and stop-dev may need a second run. Run long scripts from an agent in the foreground (`cmd.exe //d //c "<full path>\setup.bat"`).

## Word Prediction System (v4, deterministic)
- **Default engine**: `python/services/deterministic_prediction/`, a port of the GazeCompass deterministic predictor (pinned `de33a95`, stage-level parity with 0 mismatches). No network, LLM, neural model, randomness or clock: the same draft, learned state and slot lineage always give the same slots. Details: `docs/deterministic-prediction/README.md`
- **Ten word slots** on the traditional keyboard (5 top + phrase cell, 5 bottom). `word_slots` are fixed positions (`null` = deliberately empty); phrase suggestions travel separately in `sentences`
- **Execution**: runs in a separate worker process (latest-only per client, stale results dropped) — no measured impact on the 66Hz gaze loop; warm round trip ~1ms p50, <4ms max
- **Safety**: reference content policy + `python/prediction_guardrails.py` (every lexicon inflection of a blocked word is blocked too) + English-only display (`english_only_policy.v1.json`)
- **Learning**: committed actions only (accepted words, spoken messages); local `patient_data/deterministic_prediction_state.v1.json`; Delete Word undoes an acceptance
- **Tests**: `python -m unittest discover -s python/tests -p "test_deterministic_*.py"` (replays a reference parity fixture) and `npm run check:word-slots`
- **The worker process is fragile to what the backend does with its own stdio (Windows).** On 23 Sep 2026 a thread reading the backend's stdin (to notice Electron dying) made `multiprocessing.spawn` fail with "Access is denied": the worker never started and the keyboard showed no words for a whole session, while every other check passed. The backend now waits on Electron's process instead (`--parent-pid`, `watch_parent_process` in `python/main.py`). Never read stdin in the backend again, and keep `python/tests/test_port_contract.py` green: it asks a backend started the way Electron starts it for predictions
- **Legacy rollback**: `--prediction-engine legacy` or `GAZECONNECT_PREDICTION_ENGINE=legacy` (n-gram + smart bigrams + CIFG-LSTM ONNX reranker). **Datamuse API**: implemented but OFF by default (`enable_datamuse=False`)

## When Making Changes
1. NEVER break gaze functionality or dwell timings
2. NEVER break the 23" (1920×1080) tested layout — only ADD support for smaller screens
3. Use `clamp(min, preferred, max)` for responsive sizing
4. Test that all content fits within viewport on both 768px and 1080px heights
5. Keep the dark theme aesthetic (warm/dark surfaces, strong contrast, gaze accent around #2DD4BF)
6. Keep the three themes (Dark, the default; Warm; the optional Midnight Navy) and add no others. Preserve content and question/option order. Survey options and room choices use large paged grids; navigation must not overlap active choices.
