TL;DR

What it is

A fully offline, on-device prediction stack. As the patient types (by eye-gaze dwell), the app suggests the most likely next words / completions so they type fewer letters.

It fuses four signals: n-gram statistics, smart bigrams, a tiny neural language model (CIFG-LSTM), and per-patient personalization — all filtered by safety guardrails.

End-to-end request flow (one keystroke → suggestions)

  1. Type — the patient dwells on a key; KeyboardScreen.tsx appends the character and updates its text state.
  2. Emit — useWebSocket.tsx sends two messages: update_text (for the session log) and get_predictions { text, top_k: 12, lang, request_id }.
  3. Route — main.py receives it and calls _get_predictions(), which calls WordPredictionEngine.predict(text, top_k).
  4. Predict — the engine builds context, generates candidates from n-gram + smart bigrams + prefix trie, reranks them with the neural model (fusion.py blends neural + n-gram probabilities), then applies patient personalization boosts.
  5. Filter — every candidate passes through prediction_guardrails.py; blocked words are dropped.
  6. Reply — the backend sends a predictions message: { words:[{word,score,source}], sentences:[…], request_id }.
  7. Render — useWebSocket.tsx (case 'predictions') updates state; KeyboardScreen.tsx shows up to ~12 suggestions in the strip. The patient dwells one to insert it (space-committed words feed back into learning).
The neural step has a 30 ms timeout and runs off the gaze path — if it's slow it silently falls back to n-gram, so the 66 Hz eye-tracking loop is never blocked.

The prediction pipeline — how candidates are ranked

Predictions come from four cooperating signals, blended by linear interpolation, then boosted for the individual patient and filtered for safety.

Fusion formula

P_final(word) = λ_ngram · P_ngram(word)  +  λ_nn · P_neural(word) # λ_ngram is primary (default ≈ 0.75, clamped 0.50–0.90) # λ_nn is the neural weight (clamped 0.10–0.50) — semantic reranking, not the base # +15% "agreement bonus" when both n-gram AND neural rank the same word # patient-learned words get a history boost (×1.8), ranking highest overall # a neural-only word must exist in the 2,574-word ALL_VOCABULARY to survive # finally: guardrails drop any blocked word

1 · N-gram model primary

Unigram/bigram/trigram frequencies trained at startup from in-code AAC corpora + the merged vocabulary. Fast, deterministic, and the base ranker (~0.75 weight).

2 · Smart bigrams

1,339 pre-computed high-value word-pair frequencies (378 context words) that sharpen "next word given previous word." Ships as a 34 KB JSON, loaded fully at startup.

3 · Neural CIFG-LSTM semantic rerank

A tiny on-device language model that understands sentence context better than pure statistics. It reranks the n-gram candidates (~10–15% quality lift), it does not replace them.

4 · Patient personalization

Per-user recency (30-day window), patient bigrams, and a custom dictionary. Patient-learned words always rank highest (up to ~2–3× boost). Stored on disk, pruned/capped so it never grows unbounded.

The neural model (the .onnx) — deep dive

What it is

A small on-device neural language model — a "mini NLM", not a large LLM. It adds semantic understanding of context that pure n-gram statistics can't.

Type
CIFG-LSTM (Coupled Input-Forget Gate LSTM)
Shape
Embedding(128) → CIFG-LSTM(512) → Dropout(0.2) → Linear → Softmax
Params
~1.79 M
File / size
gazeconnect_lm_quantized.onnx · 1.81 MB
Vocab
661 words
Runtime
onnxruntime (CPU)

How it is trained & shipped

Training runs on the Mac (Apple-Silicon GPU) via retrain-model.sh (or retrain-model.bat on Windows), which runs python -m ml.train and exports the quantized ONNX.

Train once → benefit everywhere. The output .onnx is committed to git, so it flows automatically to Windows dev and into the shipped installer — every end user gets neural-enhanced predictions. It is not a per-session step; retrain only when deliberately changing the model, then commit the new file.

Not Gboard-level — it is far smaller than Google's models. The lean path toward better quality is to retrain this same model bigger (larger vocab + richer data), never to add a heavy LLM.

Design decisions & rationale

  • Consistency (dev-prod parity) is a hard rule. ONE model artifact is identical across Mac-dev, Windows-dev, and the shipped installer — what a developer tests is exactly what the patient gets.
  • No general-purpose local LLM anywhere — not even in dev. SmolLM2-360M / onnxruntime-genai are memory-heavy (~1–2 GB RAM) and would break parity if used only in dev. They stay a documented, theoretical future option only, never bundled.
  • Model kept as-is. The n-gram + bigram + CIFG-LSTM + personalization stack ships as-is. More quality later = retrain the same CIFG-LSTM bigger, never a heavy LLM.
  • SpeakFaster (Google, Nature Comms 2024) = paradigm only. Its real engine is a 64B cloud LaMDA that can't run on-device; only the interaction idea (initials→phrase + personalized phrase cache) is a future, offline milestone.
  • Data hygiene. Per-keystroke session logs were the only unbounded on-disk growth → now capped via session_log_keep_files (keep 20).
  • macOS dev-launch fix. Electron previously only knew the Windows venv path and fell back to bare python (absent on macOS), so the backend never started and no real predictions reached the UI. Fixed with a cross-platform resolveDevPython().

Full detail: docs/footprint-and-llm-decision.md, docs/speakfaster-lite-milestone.md, docs/word-prediction-context-and-decisions.md.
