Part I · Orientation

1. What GazeConnect Pro Is

GazeConnect Pro is a Windows desktop application that lets a person who cannot move or speak — typically a late-stage ALS / MND patient — communicate using only their eyes. A Tobii Eye Tracker 5 watches where they look; the app turns that gaze into button presses, typed sentences, and synthesized speech. It was built for one specific patient ("Papa") and, by extension, for every ALS patient who deserves to speak.

1.1 The core problem

An eye tracker is a noisy sensor. Even when a user stares perfectly still, the reported gaze point jitters by 15–60 pixels, drifts with head movement and viewing distance, and drops out entirely during blinks (frame gaps of 100 ms to several seconds). Yet the app must decide, reliably and safely, which single button the patient intends — and it must never fire the wrong one, because a wrong "Emergency" or a deleted sentence is costly for someone who types at a few words per minute. Almost every hard engineering decision in this codebase flows from that one tension: turn a noisy, gap-prone signal into calm, correct, low-latency selections.

1.2 Who uses it

  • The patient — selects everything by dwell (holding their gaze on a target for a set time). No clicking, no dragging.
  • The caregiver — configures ALS-stage timing profiles, calibrates, and manages content.

1.3 Design non-negotiables

3.1 Process topology & who launches whom

The Electron main process is the conductor. On startup it spawns the .NET bridge (which opens the TCP listener on 5555) and the Python backend (which connects to 5555 as a client and opens the WebSocket server on 8765). The React renderer connects to 8765 as a WebSocket client. This ordering matters: the bridge must listen before Python dials in, and Python must serve before the UI subscribes.

Why loopback, not one process

Each protocol boundary is also a fault boundary and a language boundary. The Tobii SDK forces .NET; the filter math and ML are natural in Python; the UI is React. Local sockets keep them decoupled and independently restartable, at the cost of two serialization hops — both trivially cheap on localhost.

In the frontend the selection is a small state machine: when gaze lands on a target, an onset delay (a short silent phase) runs; if the gaze stays, a dwell ring fills over the target's dwell time; at 100 % the button's click() fires; then a cooldown blocks the next selection so a lingering gaze doesn't double-fire.

Recent change · July 2026

The onset + cooldown were the hidden "dead time" that made typing feel sluggish (at Mid-ALS ≈ 1.4 s cooldown + 250 ms onset ≈ 1.67 s before the ring even appeared on the next key). The keyboardCadence flag — now default ON — cuts that dead time per ALS stage (Mid onset 250→150 ms, cooldown ≈1420→700 ms) without touching the dwell time or any smoothing, so responsiveness improves at zero accuracy cost. See §8.

4.2 From button click to speech

A GazeButton's onClick updates React state and, for speech, calls the app's speech router (src/utils). The router decides between native SAPI5 (via a backend WebSocket speak message handled by the Python TTS worker thread) and the browser SpeechSynthesis fallback (used for reliable Hindi/Devanagari). Careful routing prevents the classic bug of two overlapping voices speaking the same text.

Part II · The Gaze Pipeline (the backend heart)

5. Hardware & the .NET Bridge

The Tobii Eye Tracker 5 is an infrared sensor bar. Its SDK — the Tobii Interaction Library — is a Windows/.NET API, so a small C# program, tobii-helper/TobiiGazeHelper/Program.cs, owns the device. It subscribes to the "gaze point" stream, normalizes each sample to [0,1] screen coordinates, and writes newline-delimited JSON to a TCP listener on 127.0.0.1:5555. It also logs frame-gap quality (e.g. Frame gap: 290ms), which is invaluable when diagnosing "the cursor froze" reports — those are almost always tracker signal loss, not software.

Design insight

Keeping the hardware in its own process means a Tobii driver crash cannot take down the UI or the prediction engine — Electron simply restarts the bridge. The bridge is intentionally "dumb": it normalizes and forwards; all intelligence lives downstream in Python.

6. Backend Signal Processing

The Python backend (python/main.py + python/services/*) is where a noisy sample becomes a trustworthy cursor point. The pipeline is explicitly modeled on OptiKey-style dwell interaction and runs, in order, every frame:

6.1 I-VT classification (the "what kind of movement is this?" stage)

I-VT = Identification by Velocity Threshold. For each sample the classifier computes angular velocity (degrees/second). Below a threshold it is a fixation (the eye is resting — the user is probably choosing); above it, a saccade (a fast jump — the user is moving elsewhere); in between, a glissade. Onset counts and hysteresis prevent flicker at the boundary. This label is the key input to the next stages: during a fixation we smooth hard for stability; during a saccade we respond fast so the cursor keeps up.

6.2 The adaptive Kalman filter (the "estimate the true position" stage)

A Kalman filter fuses a prediction (where the model thought the gaze would go) with a measurement (the noisy sample), weighted by their relative uncertainties. The clever part here is that the measurement noise is state-dependent: during a fixation the filter "trusts the model" (large measurement noise → heavy smoothing, rock-steady cursor); during a saccade it "trusts the measurement" (small noise → snappy tracking). The per-ALS-stage presets set this directly:

# python/main.py — ACTIVE_FILTER_PROFILES (fixation state-noise grows with stage)
'balanced':  kalman state_noise = {fixation: 3500, saccade: 200, glissade: 1000}
'als_early': kalman state_noise = {fixation: 4300, saccade: 250, glissade: 1250}
'als_late':  kalman state_noise = {fixation: 5600, saccade: 320, glissade: 1650}
The One-Euro companion

Alongside the Kalman filter, a One-Euro filter (one_euro_filter.py) provides a cheap, tunable low-pass whose cutoff rises with speed — low latency when moving, strong smoothing when still. It is the standard trick for interactive pointer signals and complements the Kalman estimate.

6.3 The OptiKey 4-zone filter & magnetism

The final stage decides how "sticky" the cursor is based on where it is: a LOCK zone (already committed to a key — freeze), a KEY zone (over a button — pull to center), a FIXATION zone (resting nearby), and a FREE zone (traveling — minimal interference). Magnetism then nudges the point toward the nearest target's center within a radius, with the strength deliberately calm on dense surfaces (the keyboard uses a small 72 px/0.32 backend magnet + a 55 px nearest-center hit expansion) to avoid the "over-responsive, jumps between keys" feel.

Recent change · gaze toggle

The gaze on/off toggle used a strong 220 px capture halo that overlapped the keys above it. The toggleCalmFrontend behavior — now default ON — shrinks that to 150 px, removes the teleport-to-center, and lengthens its dwell, so reaching the toggle no longer accidentally fires an adjacent key. Crucially, the gaze-OFF → ON recovery assist is deliberately left untouched (so the patient can always turn gaze back on).

8. The Frontend Dwell Engine

Two components do almost all of the selection work:

  • GazeCursor.tsx — the real-gaze engine. A requestAnimationFrame loop that renders the cursor (direct DOM transform, not React state, for zero-lag), hit-tests the element under the point, and runs the onset → dwell → fire → cooldown state machine. This is the authority under real gaze.
  • GazeButton.tsx — the accessible target wrapper. It emits the data-gaze-context / data-gaze-dwell-ms attributes the cursor reads, and contains a separate mouse/simulation dwell engine used only in mouse-as-gaze mode.
A subtlety worth knowing

There are two dwell engines. Under real gaze, GazeCursor's rAF loop is the one that fires; GazeButton's engine is effectively dead code (mouse-only). Any change to dwell semantics must reconcile both or the simulator diverges from reality.

8.1 Dwell timing authority

All timings live in one authoritative table, src/config/dwellTimeConfig.ts (not the deprecated design.ts table). It defines per-context dwell (keyboardKey, navigationButton, emergencyButton, …) and per-ALS-stage multipliers. Stage profiles scale the whole feel:

ALS stageDwell multiplierEffect
Caregiver / Normal0.75×Fast — for non-ALS operators.
Early ALS1.0×Baseline.
Mid ALS (active default)1.35×Longer dwell, more forgiving.
Late / Advanced ALS1.8×Maximum stability & forgiveness.
Recent change · the "keyboardCadence" cadence table

A separate per-stage table (KEYBOARD_CADENCE_BY_STAGE) now supplies only the onset and post-click cooldown for keyboard/prediction targets (dwell is untouched). Default ON, it cuts the dead-time before the ring appears — Mid stage from ≈1.67 s to ≈0.85 s — and ships alongside a repeatGuard that stops an unintended look-away-and-return from triggering a fast repeat. Turning the flag off restores the previous timing byte-for-byte.

Part III · Prediction & Machine Learning

9. The Word-Prediction Engine

python/services/word_prediction.py is a five-layer, offline-first pipeline. For a patient typing at a few words per minute, a good next-word suggestion is worth many dwells, so this engine matters as much as the gaze filter.

9.1 Conversational scaffold & short words (recent)

A patient noticed that after "hello" the engine offered generic filler (the, you, want) instead of natural continuations. The cause: greetings had no bigram signal, so the model fell back to raw word frequency. The fix is a curated conversational scaffold (~60 one- and two-word contexts) applied after neural fusion so it is authoritative, but via max() so a stronger patient-learned score still wins. Now "hello" → how / good / there, "how are" → you, "nice to" → meet. A companion change lets a whitelist of common 2-letter words (is, to, be, go…) surface as genuine grammatical followers, and a +239-word general-English vocabulary (initiative, opportunity, comfortable…) was added as availability-only entries — they appear when you type their prefix without reshuffling any existing ranking.

10. The CIFG-LSTM Neural Model

The neural layer lives in python/ml/ (model.py, train.py, inference.py, fusion.py, vocabulary.py, dataset.py). It is a CIFG-LSTM — a Coupled Input–Forget-Gate LSTM, a lighter recurrent cell that ties the input and forget gates into one, shrinking parameters while keeping most of the quality. Exported to ONNX and quantized to 1.9 MB / 661-token vocab, it runs under ONNX Runtime with a hard 30 ms timeout: if it does not answer in time, the n-gram result ships and the frame is never blocked.

Fusion, not replacement

fusion.py blends the n-gram and neural scores with dynamic weights: when the n-gram signal is strong the fusion leans n-gram (λ≈0.7); when it is weak the neural model carries more (λ≈0.7 the other way). Words both models agree on get a 1.15× agreement bonus; patient words get an extra boost. The neural model only reranks recognized vocabulary — it never injects unknown or unsafe words.

11. Safety Guardrails

python/prediction_guardrails.py is the safety net that must never fail: a curated block-list of violent, harmful, and inappropriate words that are removed at generation time across every path — n-gram, neural, sentence, and patient-learned. Enforcement lives in three layers so a blocked word cannot leak from any of them.

Recent change · bilingual safety

The block-list originally held only English words — a gap for a bilingual patient. It now includes Devanagari and Hinglish harm terms (मरना, आत्महत्या, marna, zeher…), while deliberately not blocking ambiguous emotion words (उदास "sad") so the patient can still express feelings. The patient-bigram learner was also fixed so a blocked token breaks the learned chain instead of bridging its neighbours.

Part IV · Application Layer

12. Frontend Architecture

The renderer is a fairly standard React 18 app with one twist: every interactive element is a gaze target. src/App.tsx is the composition root — it mounts the context providers, defines the active routes, wires speech routing, and renders the always-present emergency path.

12.2 The 19 screens

Screens are grouped by communication need: Home, BasicNeeds, Feeling, Medical, Phrases, People, Activities, QuickWords; input surfaces Keyboard and SpatialKeyboard (a zone-first "ZoneBoard" precision layout); WebBrowsing; the home-planning trio (DesignHomeLanding, FloorPlanSurvey, CompassMap, AdvancedMap); plus Settings, Customize, and the out-of-band AlertMode. CalibrationScreen exists but is not currently routed. Every screen obeys the no-scroll, 80 px-target, dark-first rules.

12.3 The design system

src/utils/design.ts centralizes colors, typography, and spacing; sizing uses clamp(min, preferred, max) so the tested 1920×1080 layout scales down to 13″/768 px without breaking. The primary palette is dark (bg #0D1117, accent #2DD4BF) for eye comfort.

13. Electron Shell & Web Browsing

Beyond the app screens, the patient can browse the real web (mostly YouTube) using the same gaze. This is the most technically demanding subsystem, living in electron/:

  • main.ts — spawns the .NET + Python processes, owns the embedded BrowserView, and forwards gaze into it.
  • preload.ts — the safe, minimal bridge exposing a typed API to the renderer.
  • browser/browserGazeController.ts — the in-page gaze cursor: an injected script that renders a cursor, hit-tests real page elements, and runs its own dwell with progress banking, blink-gap pausing, and zoom-aware coordinate mapping.
  • browser/youtubeController.ts — reliable Play/Pause, Next, Skip-Ad, and native theater-mode full screen.
  • browser/browserViewController.ts, browserDiagnostics.ts — view lifecycle + observability.
Recent change · YouTube control bar

The Show/Hide-Controls toggle used to vanish on non-video YouTube pages (it was gated to a playing video), stranding the patient. It now works on any YouTube page and is always present in control mode alongside Show Nav, so the media controls and the nav are never a dead end.

15. Data & Persistence

  • python/data/smart_bigrams.json — 1,339 pre-computed word-pair frequencies (36 KB), merged additively into the n-gram model.
  • python/ml/ ONNX model — the 1.9 MB CIFG-LSTM.
  • Patient learning — recency timestamps + learned bigrams persisted locally; chat history feeds the personalization boosts.
  • Settings — dwell stage, theme, and customization persisted in the renderer (localStorage) and backend data files.
Performance budget

Backend pipeline <1 ms/frame; prediction ~13.5 ms mean with a 30 ms neural ceiling; the gaze path never blocks on prediction, TTS, or the (default-off) Datamuse network call — each is isolated on a worker or behind a hard timeout.

  2. src/App.tsx — providers, routing, speech, emergency.
  3. src/components/core/GazeCursor.tsx, GazeButton.tsx, config/dwellTimeConfig.ts — how selection works.

  5. python/main.py — backend orchestration + message handlers + filter presets.
  6. python/services/signal_conditioner.py → gaze_classifier.py → one_euro_filter.py — the gaze math.
  7. python/services/word_prediction.py, ml/inference.py, ml/fusion.py — prediction.
  8. electron/main.ts, preload.ts, browser/browserGazeController.ts — shell & web browsing.
  9. tobii-helper/TobiiGazeHelper/Program.cs — hardware streaming.
Golden rules before you change anything

Never break gaze functionality or dwell timings; never break the tested 1920×1080 layout (only add smaller-screen support); keep emergency always-active; every behavioral gaze change ships behind a runtime flag in gazeFlags.ts and is reversible without a code edit.

20.3 Backend interview questions you can expect

QuestionHow to answer from this project
What does the Kalman filter do here, and why "adaptive"?It fuses prediction + noisy measurement by their uncertainties; measurement noise is state-dependent (high during fixation → steady cursor, low during saccade → fast tracking), tuned per ALS stage.
What is I-VT and why hysteresis?Velocity-threshold identification of fixation vs saccade; onset counts + hysteresis stop the label from flickering at the boundary and causing cursor jitter.
How did you keep it real-time in Python?Single asyncio loop for 33–66 Hz local work; hot path never blocks — ONNX has a hard timeout, TTS is a worker thread, Datamuse is off by default and non-blocking, and the cursor renders via direct DOM writes.
How do you guarantee no unsafe prediction?Guardrails run at generation time across n-gram, neural, sentence, and patient paths (English + Hindi/Hinglish); a blocked word can't be produced, ranked, or learned.
How would you scale it to the cloud?Keep runtime gaze strictly local (privacy + latency); move only telemetry ingestion, model training, settings sync, and crash reporting to the cloud.
Why four processes?Language + fault isolation: Tobii forces .NET, filters/ML are natural in Python, UI is React; local sockets decouple them and let each restart independently.
