# OptiKey 3.2.5 gaze reference review

Reviewed 14 September 2026. Reference checkout: `/Users/rishabh/Downloads/OptiKey-3.2.5`. GazeConnect starting repository HEAD: `81dcccfbeaa5dacee78e2c8813876dd1369c541d`; the working tree already contained changes. GazeConnect observations below describe the code inspected before this task's remediation, rather than certifying the final implementation.

## Finding

OptiKey's useful design is a small, shared acquisition pipeline, adaptation to gaze movement, selection by a stable key identity, an initial intent period, recoverable partial dwell, and clear feedback. These are separate responsibilities. More smoothing and stronger locking are not automatically more accurate: they can leave the pointer on the previous target and increase correction effort.

The supplied version does explicitly list Eye Tracker 5, but routes it through the historical **EyeX SDK**. Its code is not evidence that today's ET5 SDK, driver, Windows 11, or DLL redistribution behavior is identical. It also contains bugs and historical behavior that GazeConnect should not reproduce. No source review can establish a flawless experience for every user, zero latency, or freedom from memory leaks.

This is a detailed review of the acquisition, smoothing, key/point fixation, geometry, feedback, settings, calibration and subscription lifecycle relevant to gaze interaction. It is not a line-by-line audit of every OptiKey keyboard, translation, dictionary, audio, installer, or operating-system control feature. OptiKey and a physical ET5 were not run in this macOS session.

## Actual acquisition and event path

1. The source enumeration includes `TobiiEyeTracker5`. In `CreateInputService`, ET5, 4C and several other Tobii products all instantiate `TobiiEyeXPointService`; the calibration service shares that service's `EyeXHost`. This is real ET5 routing in the supplied source, not a separate ET5 implementation. [Source enumeration](/Users/rishabh/Downloads/OptiKey-3.2.5/src/JuliusSweetland.OptiKey.Core/Enums/PointsSources.cs:14), [service construction](/Users/rishabh/Downloads/OptiKey-3.2.5/src/JuliusSweetland.OptiKey.Core/OptiKeyApp.cs:744).
2. The service checks whether the EyeX engine is available/running when its first point subscriber arrives. It creates one of two stream types and starts the host. `None` means unfiltered gaze, `Low` means lightly filtered gaze, `Medium` means sensitive vendor fixation data, and `High` means slow vendor fixation data. These are **different vendor streams**, not four sets of application damping constants. [Tobii service](/Users/rishabh/Downloads/OptiKey-3.2.5/src/JuliusSweetland.OptiKey.Core/Services/PointSources/TobiiEyeXPointService.cs:59).
3. Both callbacks reject NaN coordinates and publish screen coordinates with a new UTC receipt timestamp. The comment says the EyeX timestamp is unusable. The wrapper does not preserve hardware sample age, identify individual samples, check infinity, or expose an explicit confidence/validity field with each point. A freshly assigned receipt time cannot detect delay before the callback. [Callbacks](/Users/rishabh/Downloads/OptiKey-3.2.5/src/JuliusSweetland.OptiKey.Core/Services/PointSources/TobiiEyeXPointService.cs:95).
4. `PointServiceSource` gates samples by running state, optionally applies the local adaptive filter, applies freshness handling, maps to key identity, then uses a single-value replay and reference counting to share the sequence. It does not maintain an ever-growing gaze history. [Point source](/Users/rishabh/Downloads/OptiKey-3.2.5/src/JuliusSweetland.OptiKey.Core/Observables/PointSources/PointServiceSource.cs:47).
5. Subscribers separately consume current position, selection progress, completed selection, and a one-second sample count. UI notifications switch to the WPF dispatcher. A completed normal key selection waits 20 ms for animation before delivering its result, so the source does not support a claim of zero application latency. [Subscriptions](/Users/rishabh/Downloads/OptiKey-3.2.5/src/JuliusSweetland.OptiKey.Core/Services/InputService.subscriptions.cs:38), [result delay](/Users/rishabh/Downloads/OptiKey-3.2.5/src/JuliusSweetland.OptiKey.Core/Services/InputService.subscriptions.cs:215).

The useful separation to retain is **acquire → validate/freshness → estimate position → determine target → establish intent → accumulate valid dwell → invoke once**. Cursor drawing is feedback from that process; it must not become evidence that the eyes are still on the target.

OptiKey additionally supports individual key overrides and repeat completion sequences. These are not appropriate to import into GazeConnect's product policy: GazeConnect has exactly five fixed action durations—typing 500 ms, word suggestions/alphabet groups 1,000 ms, communication 1,250 ms, navigation/choices 1,500 ms and deliberate actions 2,000 ms. Response modes must not multiply these values or introduce repeat acceleration.

## What makes key selection tolerant

The key fixation source works with **key identity**, not a required point at the center of a key. Movement anywhere inside the same key rectangle can continue the dwell. A 250 ms initial lock-on avoids selecting merely because the eyes passed across a key. Moving to no key, a different key, or a disabled key breaks the current key fixation. [Acquisition and interruption](/Users/rishabh/Downloads/OptiKey-3.2.5/src/JuliusSweetland.OptiKey.Core/Observables/TriggerSources/KeyFixationSource.cs:137).

On interruption, it banks the time accumulated through the last sample on the old key, sets an expiration timer for that key, and clears the current fixation. On return, it can resume immediately if configured to do so. It disposes the expiration timer while that key is active again. Multiple partially completed keys can exist; completing any key clears all saved progress and timers. This reduces the cost of short excursions without confusing the abandoned key with a newly selected target. [Banking](/Users/rishabh/Downloads/OptiKey-3.2.5/src/JuliusSweetland.OptiKey.Core/Observables/TriggerSources/KeyFixationSource.cs:173), [resume](/Users/rishabh/Downloads/OptiKey-3.2.5/src/JuliusSweetland.OptiKey.Core/Observables/TriggerSources/KeyFixationSource.cs:124), [progress/completion](/Users/rishabh/Downloads/OptiKey-3.2.5/src/JuliusSweetland.OptiKey.Core/Observables/TriggerSources/KeyFixationSource.cs:221).

After completion, the fixation center is not cleared in this implementation, so a continuing gaze can repeat without redoing the original onset. Per-key completion sequences can change repeated-key timing. GazeConnect should keep a fresh-sample-based release/rearm policy appropriate to its current controls, and preserve fixed duration groups rather than importing the repeat machinery. [Completion and repeat timing](/Users/rishabh/Downloads/OptiKey-3.2.5/src/JuliusSweetland.OptiKey.Core/Observables/TriggerSources/KeyFixationSource.cs:244), [time lookup](/Users/rishabh/Downloads/OptiKey-3.2.5/src/JuliusSweetland.OptiKey.Core/Observables/TriggerSources/KeyFixationSource.cs:306).

This is **temporal tolerance**, not proof of spatial magnetism or nearest-center selection. The rectangle mapper uses the first containing rectangle; it does not search for the nearest center. [Mapping](/Users/rishabh/Downloads/OptiKey-3.2.5/src/JuliusSweetland.OptiKey.Core/Extensions/PointExtensions.cs:33).

## Point fixation differs from key fixation

For selecting arbitrary positions, OptiKey collects a bounded recent time window, calculates its center, and requires every buffered point to lie inside the acquisition radius. Once acquired, it cancels if the new sample moves beyond the fixation radius. It does not bank incomplete point dwell. The implementation also replaces the stored center with the latest point while reporting progress, so its retention center is not a permanently frozen anchor. [Point source algorithm](/Users/rishabh/Downloads/OptiKey-3.2.5/src/JuliusSweetland.OptiKey.Core/Observables/TriggerSources/PointFixationSource.cs:89).

For GazeConnect's large AAC targets, target identity and real DOM bounds are more useful than requiring physiologically motionless eyes. Geometry should use CSS pixels in the renderer after an explicit physical-screen-to-window transform. Do not copy the 40/60 pixel thresholds across different scaling factors, screen sizes, or future webcam providers.

## Smoothing: active code versus misleading similarities

The active local filter is `DataFilters/KalmanFilter.cs`. It reduces small movements and increases response to large changes using distance-dependent process noise. This explains a plausible calm-at-rest, responsive-in-transition feel. It is not a calibration algorithm and cannot determine which nearby key was intended when the tracker has a systematic offset. Its behavior is sample-step based, with no elapsed-time input, so it should not be assumed invariant across sample rates. [Filter](/Users/rishabh/Downloads/OptiKey-3.2.5/src/JuliusSweetland.OptiKey.Core/DataFilters/KalmanFilter.cs:24).

The optional pre-smoothing uses weights 0.45, 0.30 and 0.25, but stores the newly blended value as the previous measurement. Consequently it is not literally a three-raw-sample finite impulse response filter. Its default is off. The implementation also replaces accumulated estimation noise with current process noise on the following line; this is visible code behavior, not a property that a new design should recreate for parity. [Pre-smoothing and update](/Users/rishabh/Downloads/OptiKey-3.2.5/src/JuliusSweetland.OptiKey.Core/DataFilters/KalmanFilter.cs:41).

There is another file, `GazeFilter.cs`, describing gravity, damping, and a lock radius. **It is not included in the core project's explicit compile list and has no instantiation in the inspected source.** The compiled filter is the Kalman file. Therefore “OptiKey uses Kalman followed by four-zone gravity locking” is unsupported for this supplied version. [Unused class](/Users/rishabh/Downloads/OptiKey-3.2.5/src/JuliusSweetland.OptiKey.Core/GazeFilter.cs:13), [compiled filter](/Users/rishabh/Downloads/OptiKey-3.2.5/src/JuliusSweetland.OptiKey.Core/JuliusSweetland.OptiKey.Core.csproj:230).

GazeConnect's inspected baseline did stack a port-labelled adaptive Kalman implementation and a port-labelled `OptiKeyGazeFilter`; frontend comments also claimed OptiKey-style three-sample smoothing. This was not a faithful account of OptiKey's default path. Serial smoothing layers can each reduce movement while adding delay, and a frozen display cursor can conceal that the real gaze has already left the target. One position-estimation owner and independent target-selection state are easier to reason about and measure.

## Feedback, scaling, and calibration

OptiKey builds key rectangles from visible controls, `PointToScreen`, and the transform from WPF device-independent units to device pixels. It rebuilds maps for the active keyboard and listens for changing key values. This makes correct geometry part of the selection system. Logging an identical overlapping rectangle is not a complete arbitrary-overlap test. [Key geometry](/Users/rishabh/Downloads/OptiKey-3.2.5/src/JuliusSweetland.OptiKey.Core/UI/Controls/KeyboardHost.cs:696).

`CursorPopup` temporarily stops following ordinary current-position notifications while **point-selection** progress is active, but accepts the position carried in the progress event. This does not establish that OptiKey instantly freezes every keyboard cursor or always chooses the nearest target center. [Cursor behavior](/Users/rishabh/Downloads/OptiKey-3.2.5/src/JuliusSweetland.OptiKey.Core/UI/Controls/CursorPopup.cs:87).

The progress indicator supports filling a pie, shrinking, and growing. Shrinking a progress drawing is visual feedback; it is not evidence that shrinking improves sensor accuracy, nor does it shrink the key's hit area in this code. GazeConnect should keep the hit area steady during dwell and avoid moving target layouts beneath the user's gaze. [Progress rendering](/Users/rishabh/Downloads/OptiKey-3.2.5/src/JuliusSweetland.OptiKey.Core/UI/Controls/ProgressIndicator.cs:59).

Tobii calibration delegates to `EyeXHost.LaunchRecalibration()`, then treats a subsequent tracking-status event as completion. This method has no timeout, cancellation, or quantitative calibration-error validation, and subscribes after launching the request. It is not a custom method for making ET5 more accurate. GazeConnect should rely on the supported vendor calibration, then optionally validate real target access without claiming that smoothing fixed calibration. An application correction map should be saved only after independent held-out validation and invalidated when the display or calibration changes. [Calibration](/Users/rishabh/Downloads/OptiKey-3.2.5/src/JuliusSweetland.OptiKey.Core/Services/PointSources/TobiiEyeXCalibrationService.cs:18).

## Lifecycle and failure behavior to improve

- **Stale samples:** the freshness extension rejects arrivals older than TTL and emits a null on silence. However, both fixation sources explicitly filter out nulls while retaining fixation state. With a later sample on the same target, their elapsed timestamp subtraction can include missing time. A blink, stalled stream, suspension, or reconnect must not complete a dwell using time with no valid evidence in GazeConnect. [TTL](/Users/rishabh/Downloads/OptiKey-3.2.5/src/JuliusSweetland.OptiKey.Core/Extensions/ObservableExtensions.cs:21), [key null filtering](/Users/rishabh/Downloads/OptiKey-3.2.5/src/JuliusSweetland.OptiKey.Core/Observables/TriggerSources/KeyFixationSource.cs:107), [point null filtering](/Users/rishabh/Downloads/OptiKey-3.2.5/src/JuliusSweetland.OptiKey.Core/Observables/TriggerSources/PointFixationSource.cs:81).
- **Acquisition teardown:** the last point subscriber disposes the gaze/fixation stream; application exit disposes the host. This is good resource ownership. The device-status logging handler is added in the first-subscriber block without corresponding removal there, so repeated attach cycles warrant testing rather than assuming no accumulation. [Host disposal](/Users/rishabh/Downloads/OptiKey-3.2.5/src/JuliusSweetland.OptiKey.Core/Services/PointSources/TobiiEyeXPointService.cs:34), [stream disposal](/Users/rishabh/Downloads/OptiKey-3.2.5/src/JuliusSweetland.OptiKey.Core/Services/PointSources/TobiiEyeXPointService.cs:133).
- **Incomplete timers:** key completion disposes all stored timers; sequence disposal only disposes the point subscription in the inspected method. Outstanding partial-fixation timers and stored progress deserve explicit cancellation/reset on source replacement and teardown in a new implementation. [Fixation disposal](/Users/rishabh/Downloads/OptiKey-3.2.5/src/JuliusSweetland.OptiKey.Core/Observables/TriggerSources/KeyFixationSource.cs:279).
- **Nested suspension:** the input service uses a suspend request count and changes all source/trigger running states. A negative count is logged. GazeConnect should define idempotent lifecycle transitions and clear selection state when leaving an interactive route, opening a modal, losing the provider, or changing the display. [Suspension](/Users/rishabh/Downloads/OptiKey-3.2.5/src/JuliusSweetland.OptiKey.Core/Services/InputService.cs:433).
- **Configuration recreation:** many trigger values are constructor inputs. The management view flags changes requiring restart. Its vendor-processing restart check specifically compares `PointsSources.TobiiEyeX`, although ET5 shares that service. A new mode must apply atomically to all active stages and start a fresh dwell; merely changing a setting can leave old runtime values. [Restart policy](/Users/rishabh/Downloads/OptiKey-3.2.5/src/JuliusSweetland.OptiKey.Core/UI/ViewModels/Management/PointingAndSelectingViewModel.cs:517).
- **Future providers:** the UDP GazeTracker source shares the target/dwell abstraction, but suppresses repeated coordinates to detect that provider's loss behavior. That heuristic must not be generalized: a valid fixation can legitimately produce identical coordinates. Future providers need explicit sample identity, validity, age, coordinate space and capabilities. [Alternative source](/Users/rishabh/Downloads/OptiKey-3.2.5/src/JuliusSweetland.OptiKey.Core/Observables/PointSources/GazeTrackerSource.cs:71).

These are static code findings, not claims that every listed issue was reproduced on OptiKey hardware.

## Original GazeConnect behavior specification

An implementation should be written from explicit application requirements and measurable invariants, rather than a translation of OptiKey classes:

1. **One provider contract:** emit source/session identity, monotonically increasing sample identity, source timestamp where available, monotonic receipt timestamp, finite coordinates, coordinate-space declaration, tracking validity and only genuinely available quality signals. A provider must not manufacture confidence from stability or imply that webcam confidence has the same meaning as Tobii confidence.
2. **Latest data, bounded work:** callbacks deposit the newest sample in bounded storage. Network/UI queues must not accumulate old gaze. Distinguish source-sample age from transport age. Reject invalid, replayed, out-of-order, stale and wrong-session samples. Provider loss resets the active selection and filter history; reconnect needs fresh evidence.
3. **One estimator:** a newly implemented elapsed-time-aware low-pass estimator can use a shorter time constant during movement and longer one near rest. Set its initial estimate from the first valid sample. Reset after discontinuities and display changes. Validate behavior at multiple sample rates; avoid hard-coded assumptions that 133 Hz is the device rate.
4. **Separate raw evidence from display calmness:** keep the unsnapped, valid position available for target exit and stale detection. A displayed lock or snap must never keep the old target selected after fresh evidence indicates departure. Backend stabilization must not pretend it knows DOM key boundaries.
5. **Target state machine:** idle → candidate/onset → dwelling → selected/rearm. Entry uses the real target area. Retention can tolerate small measured excursions using bounded margins; it must not reach across an adjacent target's center. Returning to a saved target may resume only its own unexpired progress, after appropriate fresh evidence. Disabled, hidden, covered, moved or detached targets cannot fire.
6. **Measured dwell:** add only eligible time supported by fresh samples. Animation frames may draw progress but do not create new evidence. A long frame stall, provider pause or blink contributes no missing elapsed interval. Fixed action durations remain defined in the shared dwell configuration. Route and mode changes clear pending dwell.
7. **Unambiguous ownership:** one selector owns a physical sample and target. Electron's embedded browser needs the same freshness, cancellation and duration semantics as the React screens. Switching between host and guest must not permit a stale queued event or two selectors to trigger two actions.
8. **Honest feedback:** draw the actual candidate and its progress, keep target size stable, make pause/resume gaze accessible, and avoid presenting calibration/driver failure as low user skill. Keep Warm and Dark, no-scroll layouts, bilingual content and the existing separate Alert Mode scope.

### Modes without changing selection durations

Use a small number of complete profiles. The existing frontend and backend must agree on the same profile identity; there should not be separately editable copies of filter constants. A default is a starting point, not a guarantee for all users.

| Profile concept | Appropriate design behavior | Tradeoff to measure |
| --- | --- | --- |
| Balanced, default | Moderate smoothing, ordinary onset and bounded retention. | Establishes a predictable starting point. |
| Responsive | Less position smoothing and faster intentional target acquisition; strict stale protection unchanged. | More visible jitter for users who do not need heavy stabilization. |
| Steady | More damping near rest and modestly more target retention; rapid escape on real movement remains available. | May increase settling time; must not trap users on the wrong key. |
| Gentle, optional fourth | More forgiving brief excursions and calmer feedback, with the same fresh-evidence rule and fixed dwell groups. | Longer overall task completion and possible old-progress surprises if recovery is too generous. |

These are design recommendations, not asserted clinically optimal parameters. Avoid disease-stage labels that assume the same gaze capability for everyone with the same diagnosis. Mode selection should be a large, paged, dwell-accessible choice with a short practice task and a clear return to Balanced. Screen-specific geometry may vary, but hidden dwell multipliers must not.

## Provenance findings and distribution boundary

The supplied reference README declares GPL version 3 and includes the GPL text. The `ext/TobiiEyeXSdk` directory separately contains a November 2015 SDK license PDF. The mere presence of proprietary SDK binaries in a GPL repository does not establish GazeConnect's right to redistribute its own SDK/runtime combination. [Reference license declaration](/Users/rishabh/Downloads/OptiKey-3.2.5/README.md:25), [license text](/Users/rishabh/Downloads/OptiKey-3.2.5/LICENSE.txt:1), [bundled SDK agreement](</Users/rishabh/Downloads/OptiKey-3.2.5/ext/TobiiEyeXSdk/Tobii-EyeX-SDK-License-Agreement - November 2015.pdf>).

There was a concrete provenance issue in the inspected GazeConnect baseline. `python/services/one_euro_filter.py` explicitly described `AdaptiveKalmanFilter` and `OptiKeyGazeFilter` as ports. The first reproduced the distinctive exponential process-noise formula and covariance overwrite, and the second reproduced the damping formulas from OptiKey's unused class. These observations are stronger than the presence of the word “inspired.” The Python dwell code also described a port of incomplete fixation recovery; additional source/history review is appropriate. Baseline evidence locations were `one_euro_filter.py:761–911`, `one_euro_filter.py:921–1088` and `dwell_detector.py:145–154`. Those line positions may change during remediation.

Replacing such implementations with independently specified behavior reduces future technical dependence, but renaming classes, deleting attribution, changing the language, or removing a file from the current branch does not by itself establish clean provenance or erase previously distributed history. This review is not a legal clearance. Preserve a record of what was found and replaced; separately review repository history, assets, copied tests, packaged binaries, third-party notices, and the intended license before public distribution. No OptiKey source code or binaries were copied into this report.

For ET5 distribution, verify the current supported Tobii SDK and applicable assistive-use/redistribution terms directly with the vendor. Prefer an installer that packages only permitted app dependencies, verifies expected architecture and hashes, reports missing vendor software clearly, and directs users to supported vendor setup/calibration. Do not harvest DLLs from arbitrary installed products or infer redistribution rights from successful execution. The Windows packaging audit is a separate deliverable; this source review alone does not validate GazeConnect's installer.

## Acceptance evidence needed before sharing an installer

Use deterministic replay for invariants, then real Windows 10/11 machines and ET5 hardware for performance and usability. Synthetic replays cannot validate tracker accuracy or comfort.

- Run fixed target, edge/corner, small correction, adjacent-key transition, diagonal saccade and repeated-letter tasks at both 768 px and 1080 px viewport heights, including 1920×1080 and relevant display scaling. Record wrong selections, successful selections, corrections and time to selection, by profile.
- Replay jitter, duplicate samples, out-of-order samples, invalid/NaN/infinite input, stalled source, slow consumer, blink and reacquisition, unplug/replug, disconnect/reconnect and window/monitor/zoom changes. Assert that missing time never advances dwell and that stale data never selects.
- Exercise modal overlays, hidden/disabled elements, target removal, route transitions, gaze pause/resume, host/embedded-browser changes and rapid mode changes. Assert exactly one owner and one action per completed eligible dwell.
- Measure sample-to-render and sample-to-action timing with separately recorded stages. Report p50/p95/p99 and queue age, not just mean filter execution time. Distinguish sensor latency, transport delay, settling delay, onset and deliberate dwell duration.
- Run a multi-hour session with repeated provider connections and navigation; track process memory, thread/task counts, queue size, callback/subscription count and log growth. A short successful test does not establish absence of leaks.
- Validate a clean install on a fresh Windows VM plus a real ET5 machine, ordinary user account, offline relaunch, reboot, upgrade, uninstall, missing vendor software and missing runtime dependency. Retain build logs and a versioned bill of materials; check the final installer contents and executable signatures.

The release decision should be based on these results and user trials, with any remaining hardware, deployment or rights limitations stated explicitly.

## Browser remediation verified in this review

The browser changes made alongside this report use the existing GazeConnect implementation and the application requirements above. They do not import OptiKey code. Browser entry enables gaze once; a later Pause Gaze action remains paused. Validated samples from the new `adaptive_cursor_v1` backend bypass the browser's extra WMA/EMA stage. An explicit tracking-loss event hides and clears the embedded selector, and a source interruption longer than 1,000 ms discards pending progress.

The injected selector always excludes gaps longer than 150 ms from its dwell clock, even when older saved preferences disabled that protection. Partial-progress expiration remains based on wall time and is capped at 1,000 ms; gaps do not extend that expiration. Generated page updates also reject execution more than 150 ms after their issue timestamp, preventing a stalled page from replaying an obsolete queued gaze position into its selector.

Browser action durations now exclude onset, matching the main application: a navigation selection requires its fixed 2,000 ms after the separate intent period. All four allowed action durations are validated by replay at two different onset settings. Unknown duration values fall back to the navigation duration.

`node scripts/browser-cursor-replay.js` passed 18/18 deterministic scenarios after these changes, covering long loss, mandatory short-gap pause, TTL expiration, stale queued execution, hide/reset, four fixed durations, target-specific recovery, zoom invariance, probe acquisition, video suppression and bounded telemetry. These are synthetic execution tests of the real injected script, not ET5 hardware or Windows installer validation.

The Electron browser path now shares one outstanding slot for gaze polling and cancellation/reset work per BrowserView. Intermediate samples are dropped while the slot is busy. A source/issue timestamp is carried through the renderer hook, preload and IPC, then checked again when the page script executes and when its native click is about to begin. Pause/hide, scroll-only mode, navigation, view closure, bounds changes and zoom changes invalidate previous selection requests. A mouse button that was already pressed is released on the captured surviving view even if selection is subsequently cancelled. Explicit toolbar clicks do not require gaze eligibility.

`node scripts/check-browser-gaze-safety.cjs` passed 24 checks, including dropping 10,000 samples while a request was pending. The test executes the real request-gate class and extracts/transpiles the real native-click dispatcher to check cancellation before mouse-down, age expiration during its delay, session changes, release after cancellation and manual-click continuity.
